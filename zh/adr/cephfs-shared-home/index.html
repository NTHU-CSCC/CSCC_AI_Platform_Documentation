    ADR: 以 CephFS 取代 JuiceFS 作為跨 namespace / 跨 pod 的多租戶家目錄¶

    • 狀態：CONDITIONAL GO — 技術已在實機驗證，受限於硬體容量
    • 日期：2026-08-15
    • 決策者：平台工程
    • 原始數據：inventory/benchmark/2026-08-15/
    • 相關：.kiro/specs/production-rook-ceph-cilium-multus（Requirement 8、9），inventory/ownership-ledger/2026-08-15-storage-ownership.md

    1. 脈絡¶

    多租戶的個人 storage 必須同時掛進不同 namespace（使用者的 personal namespace、其參與的 project namespace）與不同 pod（IDE、訓練任務、fast-stage job）。在 Kubernetes 中這就是 RWX 需求。

    平台過去的兩條路都不理想：

    方案 機制 問題
    Longhorn RWX 每個 volume 一個 NFS-Ganesha share-manager pod（pkg/k8s/volume_share_nfs.go） 單點、效能差，2026-08 已退役，文件記載為「the dominant source of storage is slow reports」
    JuiceFS（現況） FUSE + TiKV metadata，static PV 複製 CSI 區塊（pkg/k8s/volume_share_juicefs.go） 每次 namespace 變更都要一次 TiKV Raft 共識，建檔 2 918 µs 且快取無效

    問題：CephFS 能不能取代 JuiceFS，同時不再掉回 NFS？

    2. 決策¶

    可以。採用 CephFS 作為跨 namespace 家目錄 lane，維持 canonical PVC + static mirror 的模式，隔離沿用現況等級（單一平台 CephX key）。

    三個理由，全部已在本叢集實測驗證：

    2.1 CephFS 原生 RWX，資料路徑完全沒有 NFS¶

    多個 pod／node／namespace 直接掛同一個檔案系統，一致性由 MDS 的 capability lease 維持。實測結果：

    PASS  same home directory visible from all namespaces and nodes
PASS  no NFS volume source and no share-manager pod (native RWX)
PASS  cross-node visibility in 208 ms (write ns-A -> read ns-C)
PASS  concurrent writes from 3 namespaces all landed
PASS  kernel CephFS mount (no FUSE)

    驗證腳本：scripts/storage/cephfs-shared-home-validate.sh（3 個 namespace × 3 個節點）。 208 ms 含 kubectl exec 往返開銷，實際檔案系統可見性遠低於此；對照 JuiceFS 需等 30 秒 entry-cache TTL。

    2.2 效能：對 JuiceFS 有數量級改善¶

    同一套 harness、同一組參數、3 次取中位數：

    Metadata 操作 local-scratch JuiceFS CephFS CephFS vs JuiceFS
    create p50 18.6 µs 2 918 µs 278 µs 快 10.5×
    unlink p50 13.1 µs 2 882 µs 275 µs 快 10.5×
    stat p50（cold） 2.80 µs 7.44 µs 5.03 µs 快 1.5×
    stat p99（cold） 3.38 µs 755 µs 11.6 µs 尾延遲好 65×

    使用者實際感受得到的工作負載（20 000 個小檔）：

    工作負載 local-scratch JuiceFS CephFS CephFS vs JuiceFS
    git init + git add -A 0.32 s 84.19 s 0.56 s 快 150×
    git status（cold） 0.06 s 1.69 s 0.09 s 快 19×
    git status（warm） 0.07 s 0.67 s 0.07 s 快 9.6×（與本機同速）
    解壓 20 000 個小檔 0.73 s 237.34 s 8.44 s 快 28×
    刪除全部檔案 0.48 s 58.28 s 9.32 s 快 6.3×
    掃描 + stat 全部 0.17 s 1.58 s 0.59 s 快 2.7×

    最關鍵的一點：git status 與 git init/add 在 CephFS 上幾乎等同本機速度（0.07 s vs 0.07 s；0.56 s vs 0.32 s），而在 JuiceFS 上分別慢 10× 與 267×。這正是使用者日常抱怨的操作。

    但誠實說明：CephFS 沒有消除與本機的差距，只是把它縮小。批次建檔／刪檔仍慢 11–19×（解壓 8.44 s vs 0.73 s）。任何分散式檔案系統都不會等於本機；延遲敏感的暫存工作仍應使用 local-scratch。

    2.3 歸因得到驗證¶

    先前的 cold/warm 拆解指出 JuiceFS 的瓶頸是遠端 metadata round-trip（stat cold p99 755 µs vs warm 8.2 µs），而 create 冷熱皆 ~2.9 ms 表示快取原理上救不了寫入——每次 namespace 變更都是一次 TiKV Raft 共識。

    CephFS 用單跳到 MDS 的記憶體 cache 取代它，實測 278 µs 正好落在事前預測的 200–500 µs 區間。假說成立。

    3. 架構¶

    沿用平台既有的 canonical / mirror 模式（spec Requirement 8），與 JuiceFS 的作法同構：

    canonical dynamic PVC (rook-cephfs-pilot SC)
  └─ subvolumePath = /volumes/csi/csi-vol-<uuid>/<uuid>
       ├─ mirror PV (ns A) : staticVolume=true, rootPath=<同上>, volumeHandle=唯一
       ├─ mirror PV (ns B) : 同 rootPath，volumeHandle 不同
       └─ ...

    實作於 pkg/k8s/volume_share_cephfs.go。pkg/k8s/volume_share.go 的 driver switch 加一個 case 即可，五個呼叫端（IDE、executor、configfile、storage control plane、fast transfer）一行都不用改。

    與 JuiceFS 路徑的三個關鍵差異：

    JuiceFS CephFS
    volumeHandle 直接沿用來源 每個 mirror 必須唯一 —— ceph-csi 以此為內部狀態索引，重複會衝突
    volumeAttributes 原樣複製 加 staticVolume: "true"、rootPath；移除 subvolumeName 等 provisioner 記帳欄位，否則 ceph-csi 會誤認 mirror 由它建立而可刪除
    reclaim policy Retain Retain（強制） —— ceph-csi 官方明示不支援 static PV 的 subvolume 刪除

    mirror 的相等性以 rootPath 比對，不是 volumeHandle——因為 handle 刻意不同。

    4. 隔離模型¶

    現階段：單一平台 CephX key，只存在於 rook-ceph namespace，租戶取不到。 隔離由 K8s RBAC 保證（租戶不能自建 static PV）。這與現行 JuiceFS 把 secret 放在 juicefs-system 的模式完全相同，不是安全退步。

    必須記錄的限制：CephFS 的 path-restricted CephX（ceph fs authorize <fs> client.X /path rw）只限制 MDS 的目錄階層。官方明言：

    "This restriction impacts only the filesystem hierarchy... Clients will still be able to access the underlying file data in RADOS directly."

    因為 osd cap 是 allow rw tag cephfs data=<fs>，涵蓋整個 data pool。因此 path 限制不可單獨作為對抗惡意租戶的安全邊界。

    升級路徑（JuiceFS 沒有的能力）：以 --namespace-isolated 建立 subvolume，讓每個租戶的資料位於獨立 RADOS namespace，再配合 per-PV nodeStageSecretRef 發放 path-restricted key。本階段先不啟用，但 subvolume 一開始就用該選項建立，日後收緊不需搬資料。

    5. 現況部署（Pilot）¶

    項目 值
    Rook v1.20.4（支援 K8s v1.31–v1.36，本叢集 v1.35.0）
    Ceph v20.2.3 Tentacle（v20.2.0 因資料毀損告警為 NO-GO）
    Ceph-CSI v3.17.0，kernel client（cephFsClientType: kernel）
    拓樸 MON×3、MGR×2、OSD×3（每 node 一個）、MDS 1 active + 1 hot standby（跨節點）
    Pool metadata + data 皆 replica 3、failureDomain=host
    容量 1.8 TiB raw → 570 GiB 可用（每 OSD 600 GiB）
    StorageClass cephfs（production lane）與 rook-cephfs-pilot（benchmark 基準，勿動），皆 non-default；longhorn 仍為 cluster default
    平台預設 lane DEFAULT_STORAGE_CLASS_NAME: cephfs —— 同時作用於 personal home 與 group storage
    網路 Cilium pod 網路，未新增 Multus NAD（B-004 未解除）

    MDS failover 已實測：刪除 active MDS 後 standby 立即接手，全程 1/1 daemons up。

    6. 這個 Pilot 不能證明什麼¶

    OSD 是 /data 上的 loop-backed 檔案，因為三台九顆 NVMe 已 100% 配置給已掛載的 XFS，且 XFS 不可 shrink（見 ownership ledger）。堆疊為：

    /data/ceph-pilot/osd0.img (fallocate 200 GiB, 非 sparse)
  → losetup --direct-io=on → pvcreate → vg_ceph_pilot → lvcreate → Rook

    疊 LVM 是因為 Rook 官方列出「LVM Logical Volumes」為支援的 OSD 型態，loop device 則完全未出現在文件中。

    因此：

    • 這不是 production 組態，不可用於容量規劃或 SLO。
    • 正面結果具結論性：CephFS 在多一層 XFS 的handicap下仍勝 JuiceFS 10×，真實硬體只會更好。
    • 資料路徑數字（fio）偏保守，metadata 數字則可信度高，因為瓶頸在 MDS 而非 OSD 吞吐。

    7. 已知問題與風險¶

    項目 說明 處置
    GPU2 容量 分配 200 GiB 後 /data 達 75%，Ceph 正確發出 MON_DISK_LOW（mon a 僅 25% 可用，門檻 30%） 保留此告警不靜音 —— 它是 GPU2 為容量瓶頸的真實訊號
    mgr 模組崩潰 已根治 prometheus mgr 模組每 15 秒向 orchestrator 要 node-proxy 硬體資料，而 Rook 的 orchestrator 未實作 node_proxy_fullreport，每次輪詢都拋 NotImplementedError 並記一次 crash —— 數小時累積 248 次，把叢集永久釘在 HEALTH_WARN，遮蔽真正的警告 停用 prometheus mgr 模組（cephClusterSpec.mgr.modules）。此處無人消費它：monitoring.enabled: false、無 rook-ceph 的 ServiceMonitor、Prometheus 的 active ceph target 為 0。停用後 150 秒內新 crash 為 0，叢集回到真正的 HEALTH_OK。日後若要 Ceph metrics，需連同 monitoring 一起開，並預期 crash 噪音回歸直到 Rook 實作該呼叫
    BlueStore probe IO error ×2 KernelDevice.cc "Unexpected IO error"，來自 OSD prepare 期間的 ceph-bluestore-tool 探測 非來自運行中的 OSD；三個 OSD 0 次重啟、26 分鐘 active+clean、已寫入 175 MiB／100k dentries。屬 loop 非受支援型態的表徵，production 應改用真實 block device
    VolumeSnapshot 未驗證 叢集完全沒有 external-snapshotter CRD（只有 snapshots.longhorn.io） 安裝需 cluster-wide 變更並會同時影響 Longhorn，刻意不做，另案決定
    static PV 限制 mirror 不支援 snapshot/clone/expand；backing subvolume 需人工清理 生命週期操作一律只對 canonical
    ceph-csi #2238 static volume 的 global mount/unmount leak 列入監控與 node runbook
    B-004 網路 25G/10G 同在 192.168.110.0/24 Pilot 走 pod 網路規避；production 前必須解決

    8. 部署過程中發現的陷阱（會讓人以為成功其實沒有）¶

    1. Rook 1.20 chart 已無 enableCephfsDriver / forceCephFSKernelClient 等 key。 Helm 靜默接受未知 values，設了等於沒設。CSI 改由 ceph-csi-operator 的 Driver CR 控制（deploy/rook-pilot/cephfs-driver.yaml）。
    2. chart 不會建立 CSI plugin 的 ServiceAccount。 缺少時 Driver CR 會回報 reconcile 成功，但 ReplicaSet/DaemonSet 靜默失敗於 error looking up service account，PVC 永遠 Pending。需套用 deploy/rook-pilot/cephfs-csi-rbac.yaml，且 csiServiceAccountPrefix 必須與其名稱一致。
    3. loop device 預設 DIO 0（buffered）。 BlueStore 的 O_DIRECT/fsync 會被主機 page cache 吸收 —— Ceph 誤以為資料已落盤（durability 風險），且寫入延遲被 RAM 灌水。必須 losetup --direct-io=on，並寫進開機 helper。
    4. MDS active 與 standby 預設可能排在同一 node（首次安裝時兩者都在 gpu1），使 standby 形同虛設。需 podAntiAffinity。

    9. 後續¶

    已完成的平台接線（2026-08-15）¶

    1. 容量擴充至 570 GiB 可用（每 OSD 200 → 600 GiB）。空間全部來自 GPU2 的 containerd 垃圾回收：810 G → 427 G，/data 由 75% 降到 54%，回收約 383 GB。成因是 201 個 image 中有 103 個未被引用，且 534 個 Active snapshot 只對應 167 個運行中容器 —— 已退出容器的 snapshot 未被清理。因此不需要動任何 Longhorn 資料就達成了 3× 擴充。
    2. CephFS 成為 personal home 與 group storage 的新建預設：DEFAULT_STORAGE_CLASS_NAME: cephfs。該值同時驅動 user_storage_manager.go（個人家目錄）與 policy_options.go（group storage 預設選項），一個值即切換兩者。既有 PVC 完全不動；JuiceFS 降為 restricted: true 的相容 lane。
    3. backend：SemanticStorageLane() 與 inferStorageBackend/RecommendedFor/Description 加入 cephfs 分支。
    4. frontend：StorageProfileBadge 的 backendFor()/badgeStyle() 加入 cephfs，補上 storage.backend_cephfs（en/zh），並把 group storage 文案改為 backend-neutral —— 原本硬寫「共享 longhorn pool / Longhorn 儲存策略」，在預設改變後會誤導。

    後續¶

    1. 未遷移任何既有 production 資料 —— 只有新建的 storage 走 CephFS。
    2. GPU2 容量瓶頸 已再處理一輪（2026-08-15）：
    3. Prometheus 的 121 G 其實是 snapshot 膨脹：60 GiB 的 volume 掛著 7 個 8–9 天前的 snapshot（72.6 GiB）。根因是 platform-daily-snapshot-delete CronJob 被 suspend（SUSPEND: True，8 天沒跑），保留策略從未生效；建立用的 platform-hourly-snapshot job 已被移除但舊 snapshot 留著。清掉後 Prometheus 由 121 G 降到 60 G。
    4. 三個 monitoring volume 已搬離 gpu2 /data，並由 1 副本提升為 2 副本跨 2 節點，順帶消除單點風險。
    5. 清除 9 個孤兒 Released Longhorn PV（JuiceFS TiKV/PD 遷移到 local-metadata 後的殘留，38.6 GiB 實際 / 1080 Gi provisioned）。Longhorn volume 由 36 降為 27。
    6. 結果：gpu2 /data/longhorn 133 G → 3.4 G，gpu2 /data 76% → 69%。
    7. 磁碟使用政策已套用：Longhorn 在 gpu1/gpu2/gpu3 一律使用 /data；/data2 於 gpu2、gpu3 皆設 allowScheduling: false，因為該磁碟存放他人以 hostPath 存取的個人資料。
    8. /data2 決定不搬遷（他人以 hostPath 存取的個人資料）。已停止新排程，既有 replica 與資料一律不動。約 1.5 TB 平台 Longhorn 資料仍在其上（harbor-gpu23-registry 433 G、platform-build-scratch 236 G、harbor-registry 187 G 為最大三筆）。

    快照回收的修正：我原先以「加總各 snapshot 的 size 欄位」估出 /data2 有 838 GiB 可回收，這個估法是錯的。Longhorn 的 snapshot size 是該快照磁碟檔的大小，而在快照鏈中最舊的那個持有幾乎全部的 volume 資料、較新的只有增量 —— 加總會把「live 資料」重複計算。實際回收只有約 17–32 GB。Prometheus 那筆（121 → 60 GiB）是真的，因為它有 7 個彼此重疊、確實過期的快照。評估 Longhorn 快照可回收量應以 volume 的 actualSize 前後差值為準，不可加總 snapshot size。 5. Longhorn numberOfReplicas: 1 仍是獨立風險：其餘 volume 多數仍為單副本。與 CephFS 無關，建議另案處理。 4. 仍為 loop-backed OSD，不可用於 SLO 或容量規劃；取得真實 block device 後需重測。 5. 決定是否安裝 external-snapshotter 以驗證 snapshot/restore。
