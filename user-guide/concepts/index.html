    Concepts & Roles¶

    How things fit together¶

    A group holds projects. A project runs workspaces and uses storage.

    Item What it is
    Group A team or lab. It has shared storage and can be a member of projects.
    Project Where your resources live. It holds the GPU/CPU quotas, config files, and deployments.
    Workspace JupyterLab or VS Code in your browser. It uses the project's quota.
    Storage volume Disk space that keeps your files after a workspace restarts.

    Quota and resource plans¶

    An admin gives each project a Resource Plan. Starting a workspace checks the project quota and your own quota. The plan also sets:

    • Allowed GPU models. The launch form only shows these.
    • A Schedule Window (when you can start work) and optional Burst Windows (when priority queues are open). See Plan Window below.
    • One or more queues you can pick, each with its own priority, preemption and GPU model rules.

    Scheduling queues, priority, and preemption¶

    Every workload picks a scheduling queue. A queue has a priority, may be preemptible, and may have a deserved GPU number:

    Concept Meaning
    Priority When GPUs are scarce, higher-priority queues go first.
    Preemptible Work in this queue can be stopped to free GPUs for higher-priority queues.
    Deserved GPU The number of GPUs the queue keeps even when other queues compete. 0 means none is guaranteed, so this queue is the first to give GPUs up.

    The workspace and deploy forms list the queues your plan allows. The default queue also needs an active plan that allows it.

    Paused instead of stopped¶

    When a preemptible workload uses one GPU and runs as a single process, the platform pauses it instead of stopping it: its memory and GPU state are saved, the GPU goes to the higher-priority job, and the workload continues from the same point on the same node once that GPU is free again. You get a bell notification when it pauses and again when it resumes. A pause can wait up to 7 days; after that the workload is stopped and reported as preempted.

    Limits:

    • Only single-GPU, single-process workloads are paused. Multi-GPU jobs, jobs that share GPU memory between processes, and jobs using CUDA unified memory are stopped as before.
    • Open network connections are closed at the pause. Reopen the notebook or SSH session after the resume; a training script that streams to an external service must reconnect on its own.
    • Work done in the last few minutes before the pause may be repeated after the resume. Writes to databases or object storage in that window can happen twice.
    • Untick Allow pausing when preempted in the deploy or workspace form for a workload that must never be paused; it is then stopped instead. The label platform-go/checkpoint: "false" in a deploy YAML does the same.
    • While paused, a job shows Paused with the pause time at the top of Pods in the project's Resources tab, and in Workspaces; the row returns to Running on its own. A paused workspace cannot be opened or started again until it resumes. Delete ends it for good, and you can then start a new one.

    Plan window¶

    A plan has two weekly time settings, both in Taiwan time (UTC+8).

    Schedule Window is when you can start work. Outside it you cannot submit anything new, even on a priority queue. The default queue follows the same rule. Work that is already running follows the plan's stop policy.

    Burst Windows open extra priority queues, but only while the Schedule Window is also open. If Burst Windows is empty, there are no priority hours.

    When a burst window closes:

    • Work that already finished is not affected.
    • About 5–6 minutes later, work still running on a priority queue is not restarted. It moves to the plan's normal queue for the same GPU model and gets that queue's priority. It can only be preempted if that queue is Preemptible. You get a bell notification.
    • If the plan has no normal queue for that GPU model, the work is stopped instead, and you get a separate notification.

    Example: the schedule is 09:00–18:00 and the burst is 13:00–15:00. Ordinary queues work from 09:00 to 18:00, and priority queues from 13:00 to 15:00. The dashboard counts down each one separately.

    Priority is not a reservation

    A priority queue puts you at the front of the line. It does not stop long jobs that are already running, so on a full cluster you may still wait for a card.

    GPU claims¶

    You get a GPU through a claim. A claim says:

    • GPU model: which GPU.
    • SM share: how much of that GPU's compute you get, as a percentage.
    • VRAM policy: elastic shares GPU memory with other workloads. hard cap sets a strict limit.

    There are two kinds:

    • Inline claim: made for you when you start a workspace. It goes away with that workspace.
    • Project GPU claim: you create it on a project's GPU Claims tab and reuse it across deployments. It takes GPU quota the moment you create it, but it only counts GPU-hours while a workload is using it.

    A project config file points to a project GPU claim through a claim slot (for example train-a). The slot name is only a label; the deploy dialog asks which claim fills it. All replicas of a Deployment share one claim and count once. If only some replicas need a GPU, split them into separate Deployments.

    GPU-hour budget¶

    A resource plan can also cap the total GPU time a project uses. One GPU-hour is one GPU running for one hour; part of a GPU counts as that part of an hour.

    An admin sets how often the budget resets for each project: monthly by default, or weekly, or every set number of hours. Your project's Overview tab shows how much you have used and when it resets. When the budget runs out, new GPU jobs and workspaces are blocked until the reset. Jobs already running keep going.

    Storage permissions¶

    • Group storage permissions come from the group. Group members always get them, and a project cannot change that.
    • The project's Storage page shows those permissions but you cannot edit them there.
    • To change a group member's access, use the group page. For project members who are not in the group, use the project page. People outside the project cannot be given storage access from the project.

    Key terms¶

    Term Definition
    Storage volume Disk space that keeps your files after a workspace restarts
    Scheduling Queue A named set of rules for priority, preemption, queue windows, and which GPU models it can use
    Plan Window Your weekly hours (UTC+8). Burst Windows add priority queues within those hours
    Preemption Stopping work in a preemptible queue so higher-priority work can run
    GPU Claim Your hold on a GPU. A project claim takes quota when you create it and counts GPU-hours only while a workload uses it
    GPU-hour One GPU running for one hour. A plan's GPU-hour budget is the most a project can use before the budget resets (monthly by default)
    Config File A deployment definition. Every save makes a new version, and old versions never change
    SM share The percentage of a GPU's compute you get
    Resource Plan A template that sets a project's GPU, CPU and memory limits, allowed GPU models, and schedule window
    Workspace JupyterLab or VS Code in your browser
