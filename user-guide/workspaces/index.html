    Workspaces¶

    A workspace is a JupyterLab or VS Code environment with GPU access. It starts from one of the platform's images.

    Who can use it: project members whose project has enough quota.

    Workspace states¶

    State What it means What you can do
    Starting The workspace is downloading its image and starting. Wait 30–120 seconds
    Running The workspace is ready to use. Open or Delete
    Stopped The workspace isn't running (for example, it hit the idle limit or the runtime limit). Files in mounted storage are kept. Delete, then create a new one
    Error The workspace failed to start. Delete, then create a new one

    There's no start or stop button. A workspace runs until you delete it or the platform removes it.

    Workspace list page¶

    Figure 1: The workspace list with status badges.

    Each row shows:

    • Workspaces — the workspace name, with the environment and project below it
    • Status — Running (green), Starting (yellow), Stopped (grey), Error
    • Image — the image it runs
    • Resources — the GPU count, or CPU for a CPU-only workspace
    • The last activity time
    • Open (only while Running) and Delete

    Below the table, a notice shows the idle limit: Auto-stop after N minutes of inactivity. See Idle shutdown below for what counts as activity.

    Launch a workspace¶

    1. Click Workspaces in the left sidebar.
    2. Click New Workspace (top-right).

    Figure 2: The new workspace form, with project, environment, image, GPU and storage fields.

    1. Fill in the form:
    Field Description
    Project The project this workspace belongs to. It decides which quota you use. Projects without a plan are marked (No Plan) and can't start a workspace.
    Internet Access Read-only. A banner under the project says whether workspaces in this project can reach the Internet (Enabled / Disabled). When it's disabled, the workspace can still reach platform services but can't download from outside.
    Environment JupyterLab or VS Code
    Image One of the platform's images for that environment: Base Notebook, PyTorch, TensorFlow, CUDA Dev, and their "(Root)" versions. Images you request or build for a project are for deployments, not workspaces.
    Root shell Makes you root inside your own container. You only see it when the project allows root containers (and, for a group's project, the group does too).
    Scheduling queue Pick one of the queues the project plan allows. See Scheduling queue and priority below.
    GPU How many GPUs. Pick No for a CPU-only workspace.
    GPU Model One of the models your plan allows. Other models are hidden.
    Compute quota (%) How much of each GPU's compute you get. 100% is a full GPU. Smaller values count as part of a GPU. If you pick a fractional GPU, it's filled in for you.
    GPU memory quota (%) How much of each GPU's memory you get. Leave Follow compute on to match the compute quota, or turn it off and set your own value. All workloads on one card add up to at most 100%.
    CPU / Memory Optional. Defaults to the plan's limits
    Shared memory (/dev/shm) Not a form field. Every workspace gets a /dev/shm of up to 8 GiB, or the memory limit if that is smaller. It lives in memory, so what you put there counts toward the memory limit. That's enough for PyTorch data loaders, NCCL and vLLM.
    Storage Volumes Tick the volumes to mount. Personal storage is at /home/<your username>; each group volume at /mnt/shared/<volume name>.

    The platform picks the name. There's no name field.

    1. Click Start.
    2. The workspace shows as Starting. Wait 30–120 seconds while it downloads its image and starts.
    3. When the status changes to Running, click Open. The IDE opens in a new browser tab.

    No storage selected

    If you have no personal storage and tick no group volume, the platform shows This workspace will not keep your files before it starts. Everything you write is lost when the workspace stops, restarts or is deleted. Click Cancel and tick a volume, or click I understand, start anyway.

    Idle shutdown

    A workspace with no activity for the idle limit shown under the list is stopped automatically, so the GPU goes back to other people. It applies to every workspace, with or without a GPU. Only real activity in the IDE counts: opening pages, typing in the terminal, running a notebook. An open tab doesn't. A workspace that is still computing keeps running, even if nobody is at the keyboard, but one that is just idling (a background process using a fraction of a core) isn't computing. Delete the stopped one and create a new one. Files in mounted storage are kept.

    Root shell

    Root shell only makes you root inside your own container. It gives you no access to the platform or to other people's data. If you don't see the toggle, ask an admin to allow root containers on the project (and on the group, for a group's project).

    Scheduling queue and priority¶

    Each workspace uses one scheduling queue. A queue has a priority, and it may be preemptible or have a deserved GPU limit. Admins set these.

    Concept Effect on your workspace
    Higher priority When GPUs are scarce, it's scheduled before workspaces in lower-priority queues.
    Preemptible queue The platform can stop your workspace to make room for a higher-priority workload.
    Default queue The lowest-priority queue, used as a fallback. It still needs an active project plan, and the plan must allow it.

    The launch form lists the queues the project's active plan allows. If the project has no plan, you can't start a workspace until an admin adds one. GPU workspaces are also checked against the GPU models your plan and queue allow, even if you leave the model blank and let the platform pick.

    Plan window¶

    A plan has two separate weekly time settings, both in Taiwan time (UTC+8).

    Schedule Window is when you can start work. Outside it, you can't submit new work, including on priority queues. Work that is already running follows the plan's stop policy. The default queue doesn't get around this rule.

    Burst Windows give you extra priority queues, but only while the schedule window is also open. If Burst Windows is empty, there are no priority hours. A workspace that is still running inside a burst window is not affected, and neither is one that already finished. About 5–6 minutes after a burst window closes, a workspace still on a priority queue is not restarted. It moves to the plan's normal queue for the same GPU model and takes that queue's priority. It can be preempted only if that queue is marked Preemptible. You get a bell notification when this happens. If the plan has no normal queue for that GPU model, the workspace is stopped instead, and you get a separate notification. The scheduling limits still apply.

    For example, say the schedule is 09:00–18:00 and the burst is 13:00–15:00. You can use ordinary queues from 09:00 to 18:00 and priority queues from 13:00 to 15:00. The dashboard shows the two countdowns separately.

    Outside the schedule, Start is rejected. Wait for the next window, or ask an admin to update the plan. The project's Plan tab also shows both countdowns.

    Connect to your workspace¶

    When the workspace is Running, click Open. Your browser connects straight to it. You don't need any setup.

    • JupyterLab opens at /lab. It's the standard Jupyter interface.
    • VS Code (code-server) opens at /. It's full VS Code in the browser.

    Where to save your work

    Code and notebooks saved under /home/<your username> (personal storage) or /mnt/shared/<volume name> (group volume) are still there after the workspace is gone. Files saved anywhere else are lost when the workspace is deleted.

    Use $XDG_CONFIG_HOME, not a hardcoded ~/.config

    Workspaces come with XDG_CONFIG_HOME=~/.local/config. Tools that follow it (code-server, pip config, gh, …) save their settings there, and the settings stay when you switch workspaces.

    If you set up a tool by hand, use $XDG_CONFIG_HOME instead of a hardcoded ~/.config.

    Stopping a workspace¶

    You can't stop a workspace. To free the GPU, click Delete. The workspace is removed, and files in mounted storage volumes are kept. Create a new workspace when you need one again.

    Bulk delete (admins)¶

    Admins who manage workspaces can tick several workspaces and delete them together with the toolbar that appears.

    How GPUs are allocated¶

    When you pick a GPU model and compute quota, the platform reserves that share of a GPU for your workspace.

    • GPU is how many physical GPUs you ask for.
    • Compute quota (%) sets the share that counts toward your quota and GPU sharing. The form shows Effective GPU, so you can see what counts against your quota.
    • GPU memory quota (%) follows the compute quota unless you set it yourself.
    • Quota counts every workspace you asked for, including ones still waiting to start.
    • Run nvidia-smi in your workspace to see which GPUs you can use.
    • To get a whole GPU or a specific model, pick 100% and a model your plan allows, or ask an admin to change the plan.

    Common questions¶

    The Open button doesn't appear even though status is Running.

    The connection can take a few more seconds to be ready. Wait 10 seconds and refresh the page. If the button still doesn't show, the workspace is probably restarting again and again. Ask your admin.

    My workspace stopped automatically.

    The platform stops a workspace when it has no activity for the idle limit (see Idle shutdown above) or when it passes the project's runtime limit. Delete it and create a new one. Files in mounted storage are kept.

    I see an error status. What do I do?

    Delete the workspace and create it again. Usual causes: the image couldn't be downloaded, you don't have enough quota, or the GPU model you asked for isn't available. If it keeps happening, send a Request.

    Can I have multiple workspaces running at once?

    Yes, as long as their total GPU use stays within your project's quota.

    My workspace was evicted with reason 'Plan window expired'.

    The schedule window closed. Create a new workspace in the next window. Burst doesn't get around the schedule. But when only the burst window closes, the workspace isn't evicted. It keeps running, moved to the plan's normal queue for its GPU model.

    Why are some GPU models greyed out in the launch form?

    Your project's plan lists which GPU models are allowed, and other models are hidden. Ask a project manager to attach a plan that includes the model you need.
