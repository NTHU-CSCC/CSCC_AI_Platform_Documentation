    Command Line Interface¶

    Use cscc-cli to sign in, build images, follow build logs, run docker commands in the IDE and manage your API tokens from a terminal.

    Who can use it: everyone who is signed in.

    Login¶

    On a new machine, tell the CLI the API URL with --api-url or CSCC_API_URL. It's fine to include /api/v1. The CLI cleans it up.

    cscc-cli login --api-url https://api.cscc.nthu.edu.tw --username alice

    The CLI asks for your password. Unlike the dashboard, it needs no CAPTCHA.

    After you sign in, the CLI saves a cscc_... API token in a config file on your machine that only you can read. The token itself shows only once, when it is created.

    To name the token:

    cscc-cli login --api-url https://api.cscc.nthu.edu.tw --username alice --name workstation

    A token name can be up to 100 characters. Without --name, the name is cscc-cli.

    Import a dashboard-created token¶

    You can also create a token in the dashboard under Settings → API Key & CLI and import it into cscc-cli:

    cscc-cli login --api-url https://api.cscc.nthu.edu.tw --token cscc_...

    The CLI checks the token before it saves it. Use this when you're already signed in to the dashboard and don't want to type your password in a terminal.

    Stateless token override¶

    For scripts, set CSCC_API_TOKEN instead of saving a config file:

    CSCC_API_URL=https://api.cscc.nthu.edu.tw CSCC_API_TOKEN=cscc_... cscc-cli whoami

    CSCC_DEV_TOKEN still works but is deprecated. Use CSCC_API_TOKEN in new scripts.

    TLS / Internal CA¶

    Official cscc-cli releases already trust the platform's certificate, so you usually don't need to set anything. If the platform certificate changes, download the latest CLI before you reconnect.

    Use the variables below only for custom builds and TLS troubleshooting:

    Env Description
    CSCC_API_URL API base URL, e.g. https://api.cscc.nthu.edu.tw/api/v1
    CSCC_API_TOKEN Optional stateless cscc_... token override
    CSCC_API_CA_CERT_PATH One or multiple PEM files separated by , or ;
    CSCC_API_TLS_SERVER_NAME Optional TLS SNI name (fallback to config if not set)
    SSL_CERT_FILE Path to a PEM file containing the internal root CA
    REQUESTS_CA_BUNDLE Alternative env path for a PEM bundle containing the internal root CA

    Example:

    CSCC_API_CA_CERT_PATH=/Users/me/platform-internal-root-ca.pem \
  cscc-cli login --api-url https://api.cscc.nthu.edu.tw --username alice

    Check Identity¶

    cscc-cli whoami

    This checks your saved token and prints your user and role. Role changes apply right away.

    Build Images¶

    Upload mode is the default. Give it a folder, a .tar.gz or a .zip:

    cscc-cli build --project <project-id> --name trainer --tag v1.0.1 .
cscc-cli build --project <project-id> --name trainer ./context.tar.gz

    If you give it a folder, the CLI packs it into a .tar.gz for you. Either way, the Dockerfile must sit at the top level.

    Dockerfile-only mode works like pasting a Dockerfile in the dashboard:

    cscc-cli build --source dockerfile \
  --project <project-id> \
  --name trainer \
  --tag v1.0.1 \
  --dockerfile ./Dockerfile

cat Dockerfile | cscc-cli build --source dockerfile \
  --project <project-id> \
  --name trainer \
  --dockerfile -

    Options:

    Option Description
    --project Project ID the image build belongs to
    --name Short image name, for example trainer-api
    --tag Optional image tag. Omit it to use the platform default
    --source upload or dockerfile
    --dockerfile Dockerfile path, or - for stdin, when --source dockerfile
    --build-arg Dockerfile ARG override as KEY=VALUE; repeatable
    --follow=false Submit the build without streaming logs

    Build arguments¶

    Pass Dockerfile ARG values at build time with --build-arg KEY=VALUE. Repeat the flag for more than one. It works with upload and dockerfile builds. A KEY starts with a letter or underscore and contains only letters, digits and underscores.

    cscc-cli build --project <project-id> --name trainer --tag v1 \
  --build-arg HF_TOKEN=hf_xxx \
  --build-arg MAX_JOBS=4 \
  .

    Use it to keep secrets and settings out of the Dockerfile you commit (for example ARG HF_TOKEN), or to limit compile parallelism (MAX_JOBS, FLASH_ATTN_MAX_JOBS, …) so a heavy build fits the shared build engine.

    Anyone who can inspect the build can see build args. Don't put anything very sensitive in them, and replace any token you pass this way once the build is done.

    Shared build queue¶

    Everyone shares one build engine, and it runs one build at a time. Each build gets a fixed amount of CPU, memory and scratch space. You can't change it.

    The build engine shuts down when nobody has built for a while. The first build after that waits about a minute for it to start.

    After you submit, --follow=true (the default) waits for the logs, shows them, and stops when the build reports completed, failed or deleted.

    The CLI gets the API address from --api-url at login, then CSCC_API_URL, then its saved config:

    export CSCC_API_URL=https://api.cscc.nthu.edu.tw

    Builds and logs use the token from cscc-cli login. You need nothing else. The project must have Image Build Permission turned on, and your project role must allow builds.

    Using docker in the IDE¶

    Your Jupyter and VS Code workspaces have a docker command that works like Docker. Each container starts next to your workspace, in the same project, and counts toward the project's quota. Nothing runs inside the workspace itself.

    Sign in¶

    A workspace started after the platform update needs no sign-in. docker uses the workspace's own identity.

    A workspace started before the update keeps the old behavior: every container is a separate job, and you sign in with cscc-cli login. docker then prints restart your workspace for full docker support. Delete the workspace and start a new one. Files in your storage are kept.

    Run a container¶

    docker run --rm alpine echo hello
docker run -d --name web -p 8080:8000 python:3.12 python -m http.server 8000
curl localhost:8080
docker ps
docker logs -f web
docker stop web

    Output streams to your terminal, and the command exits with the container's exit code.

    Without -t, Ctrl-C works like Docker's signal proxy. The first press sends SIGINT to the container's main process (the image needs /bin/sh; without one, the container is stopped instead). The second press stops the container (SIGTERM, then SIGKILL after 10 seconds). The third press detaches and leaves it stopping in the background. With -t, Ctrl-C goes to the program in the container.

    docker run -d waits until the container runs, showing Waiting: …, and then prints its ID. If the container can't start, it prints the reason, removes the container and exits 125. Press Ctrl-C to stop waiting: the container keeps starting.

    What works like Docker¶

    • Only the paths you mount are visible inside the container. Mount a folder with -v SRC:DST[:ro] or --mount type=bind,source=SRC,target=DST. Write a relative SRC as ./data or ../data: a bare data means a named volume, which doesn't exist. -v creates SRC if it doesn't exist; --mount fails.
    • SRC must be under your home folder or a group storage folder. Read-only storage stays read-only inside the container. Named volumes don't exist.
    • The image's own WORKDIR, ENTRYPOINT and CMD apply. Your command after the image name replaces CMD, and --entrypoint replaces the entrypoint.
    • Without -u, a container runs as the numeric USER the image declares (for example USER 101). If the image declares no USER, or only a name such as USER app, it runs as user 1000, the same user as your workspace, so files it writes in your storage stay editable in the IDE. -u 0, and an image that declares USER 0, run as root only when the project allows root containers (and, for a group's project, the group does too). Otherwise the container runs as user 1000.
    • A container gets 1 CPU and 4 GiB of memory unless you set --cpus and -m. --shm-size sets the size of /dev/shm.
    • -e KEY=VALUE, -e KEY (copies your value), --env-file, -w, --rm and -d work as in Docker.
    • --name takes 2 to 63 letters, digits, _, . and -, and must start and end with a letter or digit.
    • --entrypoint "" clears the image's entrypoint. Then give the command after the image name.

    GPUs¶

    Command What you get
    docker run --gpus all … or --gpus N The container shares your workspace's GPU and adds no GPU quota or GPU hours. N can't be more than the workspace has. --gpus device=0,1 picks cards by index, not by UUID.
    docker run --keep --gpus N … N new GPUs for the container, from your project's quota and plan, in the same queue as the workspace. They count toward GPU hours. With --keep, --gpus takes a number only.

    A workspace without a GPU refuses --gpus all and --gpus N with this workspace has no GPU to share; use --keep --gpus N to allocate one for the container.

    A container that shares the workspace's GPU uses the same card, so it shares the card's memory with the workspace.

    Containers and the workspace¶

    A container lives and ends with its workspace. When the workspace stops, its containers stop too. That covers deleting the workspace, the idle limit, the runtime limit and a pause. A workspace that resumes after a pause doesn't bring them back.

    A running container counts as activity. The workspace isn't stopped for being idle while one runs.

    --keep detaches a container from the workspace. It keeps running after the workspace stops and counts as an ordinary job against your project's job limits. It can't share the workspace's GPU. Stop it with docker stop.

    A container that ends stays in docker ps -a, with its logs, for 24 hours. Then it disappears. docker ps -a lists the containers you started in this project from all your workspaces, and the name of a listed container stays taken.

    A container that stopped because its workspace stopped shows as Exited (137). Its logs are gone, and docker logs answers can not get logs from container which is dead or marked for removal.

    --rm removes the container as soon as docker run has shown its exit code. For a container started with -d, the platform removes it about a minute after it exits. Without --rm, docker rm or docker container prune removes finished containers earlier.

    Stop, kill and remove¶

    • docker stop sends SIGTERM, then SIGKILL after 10 seconds. -t is accepted, but the 10 seconds are fixed. The container stays in docker ps -a as Exited (143) or Exited (137), and its logs remain.
    • docker kill sends KILL through the same path as docker stop: SIGTERM first, then SIGKILL after 10 seconds. A program that handles SIGTERM exits with 143 or 0, so the exit code isn't always 137. The container stays in docker ps -a. docker kill -s HUP (or another signal such as USR1 or INT) goes to the container's main process through a shell, so the image needs /bin/sh. The program ignores the signal unless it handles it. If the signal can't be delivered, you get could not deliver SIGHUP: ….
    • docker rm removes a finished container. docker rm -f kills a running one first.

    Ports and the browser¶

    -p 8080:8000 forwards port 8080 of the workspace to port 8000 of the container. In the workspace terminal:

    curl localhost:8080

    The port is open on localhost only, never to other machines, and only TCP works. -p 8000 alone picks a free port; docker port web shows which. If another program already uses the port, the run fails with port is already allocated before the container starts. Forwarding keeps working after you press Ctrl-C and ends when the container exits.

    To open the app in your browser, start from the workspace address (click Open). It looks like this:

    https://<platform host>/api/v1/ide/proxy/<workspace name>/

    Add proxy/8080/ to it:

    https://<platform host>/api/v1/ide/proxy/<workspace name>/proxy/8080/

    This works the same in JupyterLab and VS Code workspaces. Keep the trailing slash. The platform removes proxy/8080 before the request reaches your app. An app that links to absolute paths such as /static/app.js can't load those files through this address. Use relative links, or set the app's base path to the full address.

    Interactive containers, exec and copy¶

    docker run -it ubuntu bash
docker exec -it web sh
docker attach web
docker cp ./results.csv web:/tmp/
docker cp web:/var/log/app.log .
    • -it opens a terminal in the container. Press Ctrl-P, then Ctrl-Q, to leave a terminal session without stopping the container.
    • docker exec runs a command in a running container. It takes -i, -t, -d, -e and -w, but not -u. -e values travel in the command line, so they can appear in the platform's API logs. Pass secrets through a file in your storage instead.
    • docker attach joins the container's main process.
    • docker cp copies files in both directions through tar, so the container's image needs tar. Links are copied as links and are never followed: a copy refuses to write through one, and refuses a destination that is itself a link. It also refuses to replace a folder with a file, or a file with a folder, as Docker does.
    • An exec or attach session ends after 24 hours.

    Images¶

    docker build -t myimg .
docker run myimg
docker images

    docker build uploads the folder, builds it on the platform and stores the image in your project. It works in every project, and the FROM image can come from any registry. The platform scans base images for security problems automatically, so nothing needs approval first. -f takes a Dockerfile from any path, and --build-arg KEY=VALUE works as in Docker. After the build, a bare name such as myimg or myimg:v2 (no registry, no /) starts your build instead of a public image of the same name. docker images lists your project's builds. A .dockerignore in the folder works as in Docker, and the Dockerfile is always sent.

    Building needs the Project Manager role or above, and image builds must be turned on for the project (Image Build Permission), like cscc-cli build.

    The platform checks every image's security before the container starts. While it runs, docker run shows Waiting: image security check…. During weekday working hours the platform limits how fast it downloads from the internet, so the first start of a large image can take much longer then. docker pull only prints a reminder, because the platform fetches images when a container starts.

    Limits¶

    Limit Value
    Size 1 CPU and 4 GiB per container by default
    Project quota Container CPU, memory and GPU count toward your project's quota, and GPUs also toward GPU hours. A container that shares the workspace's GPU adds none.
    Containers per workspace 50 running or waiting. --keep containers have their own limit of 50 per project member. Beyond it, docker run fails with too many containers.
    Running at once Twice your project's per-user job limit for you in one project (20 when the project sets none), counting your workspace and its containers. Finished containers that aren't removed yet count toward a total of 60.
    Job limits A container that runs with its workspace doesn't count toward your project's concurrent job limit. A --keep container does.
    Finished containers Listed in docker ps -a, with their logs, for 24 hours after they finish. --rm, docker rm and docker container prune remove them sooner.
    Environment values -e values go straight to the container. Other project members can't see them.

    Pausing

    When the platform pauses a workspace to free its GPU (see Paused instead of stopped on the Concepts & Roles page), it stops the workspace's containers first, and the pause goes ahead. The containers don't come back when the workspace resumes.

    Commands¶

    Command What it does
    docker run Starts a container. Takes -d -i -t -e --env-file -v --mount -w -u --cpus -m --gpus --name --rm --keep --entrypoint -p --shm-size. --pull and --platform are accepted and only print a note.
    docker exec, attach, cp Run a command in, join, or copy files to and from a running container
    docker ps [-a] [-q] [--format] [-f] List your containers in this project, from all your workspaces. -a adds the ones that finished in the last 24 hours.
    docker logs [-f] [--tail N] [-t] [--since] Show a container's output
    docker stop [-t N], kill [-s SIGNAL], rm [-f] Stop (SIGTERM, then SIGKILL after 10 seconds), send a signal, or remove containers
    docker wait, inspect, port Print exit codes, details or published ports
    docker build, images, pull Build an image, list your project's builds, print a reminder
    docker container ls, rm, prune, docker system prune The long forms. prune removes finished containers only.
    docker info, version Show your project, queue and GPUs

    These don't exist, and each prints a line saying what to do instead:

    Not supported Why
    compose, network, volume There is no multi-container runtime, no user-defined network and no named volume. Start each service with docker run -d, and mount folders from your storage.
    push, commit, save, load, tag, rmi Images stay in your project. Use docker build -t NAME:TAG.
    start, restart, pause, unpause A finished container can't start again. Run a new one.
    stats, top, events The platform doesn't collect them. Use docker exec NAME top, or docker ps and docker wait.
    login The workspace is already signed in.
    -P, --network, --privileged, --cap-add, --device, --restart, --ipc, --pid, UDP ports, exec -u Containers share the platform's network, run isolated, never run privileged, and can't add Linux capabilities.

    Troubleshooting¶

    What you see What it means
    Waiting: image security check… stays on screen The container hasn't started. A new image waits for its security check, and a busy queue waits for resources. Leave the command open, or run with -d and follow it with docker logs -f.
    Exit code 125 The container never started: the image couldn't be fetched (for example pull access denied), was rejected by the security check (the reason starts with Image security check failed), or an option was invalid. The reason prints above the exit, and the container is removed for you.
    Exit code 126 or 127 The command in the image isn't executable (126) or doesn't exist (127). Check the image's ENTRYPOINT and your command.
    Exit code 143 docker stop, docker kill or Ctrl-C ended the container with SIGTERM.
    Exit code 137 The container was killed. It ran out of memory (docker inspect NAME shows "OOMKilled": true, so raise -m), it ignored SIGTERM for 10 seconds, or its workspace stopped.
    Permission denied or Operation not permitted right after start, for an image such as nginx The image's main process needs root, and the image declares no numeric USER, so the container runs as user 1000. Add -u 0 in a project that allows root containers, or use an unprivileged variant of the image, for example nginxinc/nginx-unprivileged.
    port is already allocated A program or another container already uses that port of the workspace. Pick another host port, and check docker ps.
    Conflict. The container name "/web" is already in use A container with that name still exists, even if it finished in the last 24 hours. Run docker rm web, or choose another name.
    Invalid container name Use 2 to 63 letters, digits, _, . and -, starting and ending with a letter or digit.
    can not get logs from container which is dead or marked for removal The container's logs are gone: its workspace stopped, or it was removed.
    this workspace has no GPU to share The workspace has no GPU. Use --keep --gpus N, or start a workspace with a GPU.
    is outside your workspace storage or named volumes are not supported Mount a folder under your home or a group storage folder.
    invalid or expired workspace token Retry once. If it persists, delete the workspace and start a new one.
    restart your workspace for full docker support The workspace is older than the update. Delete it and start a new one.

    Token Management¶

    List your active API tokens:

    cscc-cli tokens list

    Revoke a token by ID:

    cscc-cli tokens revoke <token-id>

    Sign out on this machine:

    cscc-cli logout

    Logging out revokes the token you're using and removes it from the config file. Certificate settings you added by hand stay, so you can sign in again without redoing them.

    Defaults¶

    Setting Default Notes
    Token lifetime 90 days Make a new token when the old one expires
    Active tokens per user 20 Revoke unused tokens if you hit the limit
    Failed sign-ins before lockout 5 Applies to both the dashboard and the CLI
    Lockout duration 15 min Wait, or ask an admin to unlock your account

    Admins can change these values.
