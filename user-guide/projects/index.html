    Projects¶

    A project is where your resources come from. Every workspace you start uses a project's quota, and every config file and deployment belongs to a project.

    Who can use it: everyone who is signed in. You get a personal project automatically when you register.

    Project page layout¶

    Figure 1: Projects list in list view, the default.

    The Projects page has two views:

    • List view (default) — a compact table with sortable columns
    • Grid view — cards with the project name, description, member count and GPU usage bar

    Switch views with the icons at the top right of the toolbar.

    Create a project¶

    You need the manage-projects permission to create a project. Without it, the New Project button is hidden, and the create page sends you back to your project list. Ask an admin to create a project for you. You already got a personal project when you registered.

    1. Click Projects in the left sidebar.
    2. Click New Project (top right; you only see it with the manage-projects permission).
    3. Fill in the project form:
    Field Description
    Name Short identifier (alphanumeric, hyphens allowed)
    Group Owning group (required)
    Description Optional. What the project is for
    1. Click Create. The project shows up in your list right away.

    Quota is assigned by an admin

    A new project starts with zero GPU quota. Ask your admin, or send a Request, to have a Resource Plan attached to your project.

    Project detail tabs¶

    Click a project to open it. Everyone sees the Overview, Config, Plan, Builds, GPU Claims and Resources tabs. Ray shows up when the platform has Ray sessions turned on. Members, Storage and Settings show up depending on your role.

    Figure 2: The project page, with the Overview, Config, Plan, Builds, GPU Claims and Resources tabs, plus tabs that depend on your role.

    Tab Contents
    Overview Description, quota usage chart, GPU-hour budget, current plan, member summary
    Config Config files with versions. They describe what you want to run
    Plan The project's resource plan, schedule window, allowed GPU models and quota limits
    Builds The project's image builds: pick an archive or a Dockerfile, see the shared queue and read live build logs
    GPU Claims GPU reservations you create ahead of time and attach to a deployment later
    Resources What you run, in one tab per kind (Pods, Services, …), and live GPU, CPU and memory use. Managers also see every member's
    Ray Your Ray sessions, or the address to submit Ray jobs to. Shown only when Ray sessions are turned on
    Members / Storage Extra tabs, shown when your role lets you manage members, quotas or storage
    Settings Limits for every workspace in the project. See Project settings below

    Who sees what: the Storage and Settings tabs need Project Manager or above. Only Project Admins see the Members tab. (Platform admins must switch to Admin View in the avatar menu to count as a Project Admin.) An Admin can't demote themselves, so a project always keeps at least one Admin.

    Project settings¶

    The Settings tab (Project Manager or above) has limits that apply to every workspace in the project:

    Field What it does
    Max workspace continuous runtime In seconds. A workspace that has run longer than this is stopped automatically. 0 means no limit (the default).

    Click Save Changes to apply it. The limit also applies to GPU desktops started from this project.

    Build project images¶

    Use the Builds tab when the project needs an image of its own. The base image in your Dockerfile FROM line can come from any registry. The platform scans base images for security problems automatically, so there is no approval step. Project Managers and Project Admins can start builds if image builds are turned on for the project. Project Members can see build status and logs. A member can't start a build, but can delete the image from a finished build they started.

    Source options¶

    Source When to Use It
    Upload archive Upload a .tar.gz or .zip. Put the Dockerfile at the top level of the archive.
    Dockerfile only Paste a Dockerfile. The platform sets up the rest of the build for you.

    Build settings¶

    Field Notes
    Image Name Short name, for example trainer-api. The platform makes the full registry path.
    Tag Optional. Leave it empty for the platform default, or use a version like v1.0.1.
    Build source Upload archive or pasted Dockerfile.

    Builds go into a shared queue and run one at a time. Each build gets a fixed amount of CPU, memory and scratch space. You can't change it in the form, and it doesn't use your project or personal quota.

    The build engine shuts down when nobody has built for a while. The first build after that waits in the queue for about a minute while the engine starts, then runs as usual. The message says it is waiting for the build engine.

    The platform checks uploaded archives for unsafe paths and size limits before the build starts.

    The build history shows status, source type, destination image and live logs. Failed builds show a short summary in the table. Click the log button for the full output. If a build is retried, the log view keeps the previous attempt's failure reason above the current one.

    Each build row has icon buttons: Cancel build while it runs (or Delete image artifact once it has produced an image), Clear saved logs and Delete history record. Builders and project managers can clear saved logs for finished or failed builds. Build history and images are not touched. The member who started a finished build, or a project manager, can delete its image artifact. Clear my completed build images deletes every finished image you built in this project, and keeps the build history and saved logs. A tag ID that appears more than once is deleted once.

    Delete history record removes only the history and saved logs. It doesn't delete the image artifact. Harbor frees the registry space in its daily garbage collection. A recently uploaded image may need two garbage collection runs before it can be removed.

    Build access is project-governed

    If you don't see the start form, either the project doesn't have Image Build Permission turned on, or your project role can't start builds. You can still see build history and logs. Ask a project manager or platform admin to change the project setting or your role.

    GPU Claims¶

    The GPU Claims tab lists GPU reservations you can create for a project before you deploy anything. A claim holds GPU quota as soon as you create it, but only counts GPU-hours once a running workload uses it. When a config file has a GPU claim slot, you pick a claim for it in the deploy dialog.

    Create a claim¶

    Fill in the Create GPU ResourceClaim form and click Create:

    Field Notes
    Claim name The name you use when you attach this claim to a deployment. Letters, digits and hyphens only.
    GPU device class The GPU model to reserve. The form starts with a specific model. Pick Any only if the model doesn't matter.
    GPU count How many physical GPUs this claim reserves. A claim with several GPUs is still one reservation.
    SM share Compute share from 1% to 100%. The effective GPU count shows next to the form.
    VRAM mode Elastic shares GPU memory with other workloads. Hard cap keeps to the percentage you pick.
    VRAM share Only used with Hard cap. The memory is worked out from the smallest card of that model.

    Every replica of a Deployment shares the same claim. A 2-GPU claim is one 2-GPU reservation however many replicas run. Quota and GPU-hours count once per claim, not once per replica.

    A claim that isn't attached to anything uses 0 GPU-hours but still counts against the project and per-user GPU quota. The table columns are Name, Owner, GPU, SM, VRAM, Status and Allocation, plus a delete icon. Status is Reserved (created, nothing attached), Allocated (a GPU is assigned) or In use by . You can delete unused claims, but not one a running workload is using.

    Claim ownership

    Project Members can create their own claims. Project Managers can also see and delete other members' claims.

    Plan window countdown¶

    The Plan tab shows two countdowns, one for scheduling and one for priority, in Taiwan time (UTC+8). Schedule Window always decides when work can start.

    • Window closes in HH:MM:SS is how much time you have left.
    • Window opens in HH:MM:SS is when you can start work again.
    • Always active means no weekly schedule limit.

    The deploy dialog warns you before scheduling closes. After it closes, you can't start new deployments, and switching queues doesn't help. Workloads already running follow the plan's stop policy.

    If the plan has Burst Windows, you see Priority ends in HH:MM:SS or Priority starts in HH:MM:SS, based on where they overlap the schedule hours. Priority queues show up next to the ordinary queues only during that overlap. When burst closes, existing work keeps running and scheduling stays open. A deployment that is still running inside the burst window, or already finished, is not affected. About 5–6 minutes after burst closes, a deployment still on a priority queue moves to the plan's normal queue for the same GPU model and takes that queue's priority. It can be preempted only if that queue is marked Preemptible. You get a bell notification when this happens. If the plan has no normal queue for that GPU model, the deployment is stopped instead, and you get a separate notification. If a window changes while the deploy dialog is open, the dialog refreshes the queue choices, keeps your selection if it's still available, and clears old validation results.

    A queue can also have a runtime limit. If the queue you picked has one, your workload is stopped automatically after that many seconds, and the bell shows a Runtime limit reached notification. An admin sets the limit. You can't raise or turn it off in your config file.

    If the plan has a GPU-hour budget, the Overview tab also shows a GPU-hours bar. It shows the GPU-hours used this period against the budget, the reset period (monthly, weekly, or every N hours, set by an admin) and when it next resets (UTC+8). When the budget runs out, you can't start new GPU jobs or workspaces until the reset. Jobs already running are not affected.

    Which images a project can run¶

    Images you build in a project are private to that project's members. Another project can't run them, and you can't run theirs. A project can run:

    • images it built itself;
    • images of the platform, such as the ready-made IDE and desktop images;
    • public images from Docker Hub, GHCR and NVIDIA NGC, through the platform mirrors;
    • older images built before builds became private to each project: an image you built yourself works only in your personal project, and an image a group built works only in projects that group owns.

    When a job or workspace uses an image another project built, the Image security checks card shows an Error row with the reason Image security check refused: <ref>: built by another project; use this project's images, platform images or public mirrors. Rebuild the image in your own project, or ask the project that owns it to share the Dockerfile. The same rule applies to the FROM line of your Dockerfile: a build is rejected when its base image belongs to another project.

    Image security checks¶

    The Overview tab has an Image security checks card. It lists the last 10 images your project's jobs and workspaces started, with a status for each:

    Status Meaning
    Checking The platform is still checking the image. The card refreshes by itself.
    Passed The image passed the check.
    Failed The image has a serious known vulnerability that has a fix.
    Error The check could not finish, for example the image or tag does not exist, or the check timed out.
    Unsupported The image comes from a registry the platform cannot check.

    Each row also shows a one-line reason and when the image was last used. A Failed row says either would be blocked once enforcement is on or blocked. While enforcement is off, the job still runs; once it is on, the job does not start. When the platform has image checks turned off, the card says Image security checks are turned off.

    Click a Failed row to see How to unblock: each package to upgrade, from your installed version to the fixed version, with the packages that cause the failure first and the other recommended upgrades folded below. A Passed row shows Recommended upgrades, or says that no upgrade is needed. Vulnerability IDs are not shown; only administrators see them. Issues that have no fix yet are only counted, because they do not block. The other statuses have no details to open.

    To fix a failure, rebuild your image on a newer base image tag, or upgrade the listed packages in the Dockerfile with the image's package manager (for example apt, apk, dnf or pip) to at least the fixed version, then run the job again. For a public image, such as one from Docker Hub, pick a newer tag. For a platform image, choose another version or contact the administrators.

    The card shows the latest result per image, not a history. When an 11th image is used, the oldest row is removed.

    Config file versioning¶

    Every save creates a new version. Old versions are never overwritten, so you can always look at an earlier one or deploy it again. Edit or upload a config file, save it, and a new version appears. You can deploy any version.

    Working with config files¶

    1. Go to Projects → [your project] → Config tab.
    2. Click New File, then upload a YAML file or paste content in the editor.
    3. Each save creates a new version.
    4. Click the History icon next to a config to view all versions.
    5. To deploy a specific version, click Deploy on the version row.
    6. In the deploy dialog, pick the scheduling queue. If the YAML has GPU claim slots, pick one of your reserved GPU claims for each slot. This applies to this deploy only.

    Running instances show up in the project's Resources tab, described below.

    A finished Pod is removed at most three days after it ends, and its entry and logs in the Resources tab go with it. The logs can disappear sooner, for example when a node restarts. A Job keeps its finished pods until you delete the Job. Save results, and anything else you want to keep, to a mounted storage volume while the run is going.

    Containers you can shell into¶

    To open a Terminal in a container, the container has to keep running. A shell with no arguments, such as command: ["/bin/sh"], exits right away. The container then restarts again and again, and every terminal attempt fails.

    Give the container real work:

    command: ["sleep", "infinity"]

    or keep the shell alive by turning on stdin and tty under Interactive shell in the Resource Wizard (stdin: true and tty: true in raw YAML). The wizard warns you when a bare shell would exit right away.

    Once the container is running, open the project's Resources tab, stay on Pods, and click Terminal on the row. Deployments and Jobs have no terminal button; the running instance they created is under Pods.

    Deploy rules¶

    Quota is checked against everything you already have going, so a workload still waiting to start keeps its share until it finishes or is removed. Config files can deploy Pod, Deployment and Job. Other kinds are rejected.

    Every container must set both a memory request and a memory limit of at least 128Mi. Deploy and dry-run validation reject missing values. Always write the unit: a bare memory: "1" means one byte and is rejected.

    Asking for a GPU¶

    A config file can ask for a GPU in two ways.

    • Inline GPU request. In the Resource Wizard, pick a GPU model in the container's resource settings. The platform counts it toward your quota, checks the model against your plan's allowed models, and sets up the GPU when you deploy.
    • Reusable GPU claim. In the Resource Wizard, choose Pick at deploy and give the slot a name such as train-a. The slot name is only a label. In the deploy dialog, you pick which of your own claims from the GPU Claims tab goes with it.

    To give a claim to only some replicas, split them into separate Deployments. A config that asks for no GPU needs no allowed-model list and never gets a GPU claim.

    Advanced: writing the YAML yourself

    Leave the fields the platform manages out of your YAML: don't set metadata.namespace, metadata.generateName, metadata.ownerReferences or metadata.finalizers. For storage, use {{userVolume}} to mount your personal volume. Naming a volume directly works only in a group's project, and only for volumes that group already has.

    • Each pod gets one memory-backed /dev/shm, shared by its regular containers (not init containers), of up to 8 GiB or the pod's memory limit if that is smaller. It is skipped when any container in the pod already mounts something under /dev/shm.
    • An inline GPU request goes straight into the container's resource requests, for example nvidia.com/rtx6000: "1".
    • A GPU claim slot is an annotation on the Pod, or on the Deployment's template: platform-go/dra-claim-name: '{{ gpuClaimName "train-a" }}'. {{gpuClaimName}} with no name still works as the default slot. Two workloads can share a slot deliberately, or use different slots to get different claims.

    Config files and deployments require Project Manager role

    Only project members with the Manager role or higher can create, edit, deploy, validate, inspect or delete config-file instances.

    Managing members¶

    1. Open the project and go to the Members tab.
    2. Click + Add Members (you need the Project Admin role).
    3. Search by username or email.
    4. Pick a role for each user:
    Role What they can do
    User Launch workspaces, view configs
    Manager Edit configs, manage deployments
    Admin Add/remove members, set member quotas
    1. Click Confirm to save.

    Project Admins can tick several rows to remove members, change roles or set per-user quotas all at once. Managers and Admins see everyone's quota. A Project User sees only their own. A quota of 0 means no limit for that member, but the project plan's cap still applies.

    Group-inherited members. Members who joined through the owning group can be part of a bulk quota change, but not a bulk remove or role change. Change their membership and role in the group instead.

    Removing a direct member also removes their workspace area in the project, any project storage permission overrides and their per-user quota. To remove a member who came through the group, remove them from the group.

    Group inheritance and effective project role¶

    When a group owns a project, the platform works out your project role like this:

    1. If you were added to the project directly, that role wins (admin / manager / user).
    2. Otherwise, on a personal project, the owner counts as admin.
    3. Otherwise, your group role in the owning group is your project role. So a Group Admin acts as a Project Admin on every project the group owns, even if nobody added them to the project.

    That's why a Group Admin can set per-user quotas on their group's projects, and see the bulk-select controls in the Members tab, without being added as a member.

    When someone leaves the lab: ask an admin to remove them from the group. They lose access to every project they joined through that group. You don't need to clean up project by project.

    Deleting a project¶

    Only a platform admin can delete a project, from Admin → Projects. The project page has no delete button. Ask an admin, or send a Request, and delete the project's workspaces first. What happens:

    • The config version history and deployment records are gone for good.
    • Storage volumes are not deleted. They stay on the Storage page.

    Resources tab¶

    The Resources tab shows what is running in the project and how much it uses.

    Your own resources. The cards at the top show your GPU, CPU and memory use. Below them is one tab per kind: Pods, Services, Deployments, StatefulSets, Jobs, ConfigMaps, Secrets, Ingresses, ResourceClaims and RemoteDesktopSessions, each with a count. Pods opens first. Paused jobs sit at the top of Pods, because their Pod is gone until they resume. Delete all removes everything you have in the project and frees the quota it held.

    Everyone's resources. Project Admins, Project Managers and platform Admin/Manager roles get Personal and Members at the top of the tab. Members lists every other member:

    Column Meaning
    User Project member
    GPU Effective GPU units currently used
    CPU Requested or observed CPU cores
    Memory Memory in MiB
    Pod (the running instance) How many that member has running now

    Search by name, or expand a member to see what they run in the same kind tabs. Delete on a member's row removes all of that member's resources and frees their quota. Regular Project Users see only their own resources.

    On Pod rows, hover, focus, or tap the status badge to see recent events. This helps when a workload looks like it's still starting but is really failing to pull its image.

    GPU quota overview¶

    The Overview tab shows a quota bar for each resource type:

    Resource What It Tracks
    GPU Effective GPU units consumed vs. plan limit
    CPU CPU cores consumed by running workspaces
    Memory RAM consumed by running workspaces

    If the GPU bar is full (100%), a new workspace waits in the queue until resources free up.

    Common questions¶

    I don't see a New Project button.

    Only users with the manage-projects permission see it. If you don't have it, ask an admin to create a project for you. Your personal project was created when you registered.

    How do I view old config file versions?

    On the Config tab, click the clock icon (History) next to a config file. You see every past version with its time.

    My project quota is 0 GPUs. How do I get more?

    Send a Resource Request through Requests. An admin reviews it and attaches a Resource Plan to your project.

    What's the difference between a workspace's GPU and a GPU Claim?

    A workspace holds its GPU only while the workspace exists. A GPU Claim is a separate reservation that stays across deployments. Use one when several jobs need the same fractional GPU and you don't want them rescheduled each time.

    Why is the Deploy button disabled?

    Either the project has no active plan, or its schedule window is closed. The default queue doesn't get around this. Check the Plan tab for the next opening time.
