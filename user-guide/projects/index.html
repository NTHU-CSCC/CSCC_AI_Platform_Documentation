    Projects¶

    A project owns your quota, config files and deployments. Every workspace you start uses a project's quota.

    Who can use it: everyone who is signed in. Registering creates your personal project.

    Project page layout¶

    Figure 1: Projects list in list view, the default.

    Switch views with the icons at the top right of the toolbar:

    • List view (default): a table with sortable columns
    • Grid view: cards with the project name, description, member count and GPU usage bar

    Create a project¶

    Creating a project needs the manage-projects permission. Without it, New Project is hidden; ask an admin to create one for you.

    1. Click Projects in the left sidebar.
    2. Click New Project (top right).
    3. Fill in the project form:
    Field Description
    Name Short identifier (alphanumeric, hyphens allowed)
    Group Owning group (required)
    Description Optional. What the project is for
    1. Click Create.

    Quota is assigned by an admin

    A new project has zero GPU quota. Send a Request to have an admin attach a Resource Plan.

    Project detail tabs¶

    Everyone sees Overview, Config, Plan, Builds, GPU Claims and Resources. Ray appears when Ray sessions are turned on; Members, Storage and Settings depend on your role.

    Figure 2: Project detail tabs.

    Tab Contents
    Overview Description, quota usage chart, GPU-hour budget, current plan, member summary
    Config Config files under version control: what you want to deploy
    Plan The project's resource plan, schedule window, allowed GPU models and quota limits
    Builds The project's image builds: pick an archive or a Dockerfile, see the shared queue and read live build logs
    GPU Claims GPU reservations you create ahead of time and attach to a deployment later
    Resources What you run, in one tab per kind (Pods, Services, …), and live GPU, CPU and memory use. Managers also see every member's
    Ray Your Ray sessions, or the address to submit Ray jobs to. Shown only when Ray sessions are turned on
    Members / Storage Extra tabs, shown when your role lets you manage members, quotas or storage
    Settings Limits for every workspace in the project. See Project settings below

    The Storage and Settings tabs need Project Manager or above. Only Project Admins see Members (platform admins must switch to Admin View in the avatar menu). An Admin can't demote themselves, so a project always keeps one Admin.

    Project settings¶

    The Settings tab (Project Manager or above) sets limits for every workspace in the project and holds its Docker Hub connection:

    Field What it does
    Max workspace continuous runtime In seconds. A workspace that has run longer than this is stopped automatically. 0 means no limit (the default).
    Docker Hub Username and access token for private Docker Hub images. See Use private Docker Hub images below.

    Click Save Changes. The limit also applies to GPU desktops from this project.

    Build project images¶

    Use the Builds tab when the project needs its own image. The FROM image can come from any registry; the platform scans it automatically, with no approval step. Project Managers and Admins can start builds when image builds are on for the project. Project Members can see status and logs, and delete the image of a finished build they started, but cannot start builds.

    Source options¶

    Source When to Use It
    Upload archive Upload a .tar.gz or .zip. Put the Dockerfile at the top level of the archive.
    Dockerfile only Paste a Dockerfile. The platform sets up the rest of the build for you.

    Build settings¶

    Field Notes
    Image Name Short name, for example trainer-api. The platform makes the full registry path.
    Tag Optional. Leave it empty for the platform default, or use a version like v1.0.1.
    Build source Upload archive or pasted Dockerfile.

    Builds run one at a time from a shared queue. Each gets fixed CPU, memory and scratch space that doesn't count against your quota. The platform checks uploaded archives for unsafe paths and size limits first.

    The build engine shuts down when idle, so the next build waits about a minute for it to start.

    The build history shows status, source type, destination image and live logs. A failed build shows a short summary; click the log button for the full output. After a retry, the log view keeps the previous failure reason above the current one.

    Each build row has icon buttons: Cancel build while it runs (Delete image artifact once it has produced an image), Clear saved logs and Delete history record.

    • Clear saved logs: builders and project managers can clear logs of finished or failed builds. History and images stay.
    • Delete image artifact: the member who started a finished build, or a project manager.
    • Clear my completed build images: deletes every finished image you built in this project. History and saved logs stay. A tag ID that appears more than once is deleted once.
    • Delete history record: removes only the history and saved logs, not the image artifact. The image registry frees the space in its daily garbage collection, and a recently uploaded image may need two runs before it can be removed.

    Build access is project-governed

    No start form means the project has Image Build Permission off or your role can't start builds. You can still see build history and logs. Ask a project manager or platform admin to change it.

    GPU Claims¶

    The GPU Claims tab lists reservations you create before you deploy; see GPU claims. A config file's claim slot gets a claim in the deploy dialog.

    Create a claim¶

    Fill in the Create GPU ResourceClaim form and click Create:

    Field Notes
    Claim name The name you use when you attach this claim to a deployment. Letters, digits and hyphens only.
    GPU device class The GPU model to reserve. The form starts with a specific model. Pick Any only if the model doesn't matter.
    GPU count How many physical GPUs this claim reserves. A claim with several GPUs is still one reservation.
    SM share Compute share from 1% to 100%. The effective GPU count shows next to the form.
    VRAM mode Elastic shares GPU memory with other workloads. Hard cap keeps to the percentage you pick.
    VRAM share Only used with Hard cap. The memory is worked out from the smallest card of that model.

    All replicas of a Deployment share one claim. Quota and GPU-hours count once per claim, not per replica.

    An unattached claim uses 0 GPU-hours but still counts against project and per-user GPU quota. Status is Reserved (nothing attached), Allocated (a GPU is assigned) or In use by . You can delete unused claims, not one a running workload uses.

    Claim ownership

    Project Members can create their own claims. Project Managers can also see and delete other members' claims.

    Plan window countdown¶

    The Plan tab shows a scheduling and a priority countdown in Taiwan time (UTC+8). Schedule Window decides when work can start; see Plan window.

    • Window closes in HH:MM:SS is how much time you have left.
    • Window opens in HH:MM:SS is when you can start work again.
    • Always active means no weekly schedule limit.

    The deploy dialog warns you before scheduling closes. After that you can't start new deployments on any queue; running workloads follow the plan's stop policy.

    With Burst Windows, you also see Priority ends in HH:MM:SS or Priority starts in HH:MM:SS. Priority queues appear only where burst overlaps the schedule hours. When burst closes, scheduling stays open and existing work keeps running; see Plan window for deployments still on a priority queue. If a window changes while the deploy dialog is open, it refreshes the queue choices, keeps your selection if still available, and clears old validation results.

    An admin can set a runtime limit on a queue. If your queue has one, your workload stops after that many seconds and the bell shows Runtime limit reached. Your config file can't raise or turn it off.

    With a GPU-hour budget, Overview shows a GPU-hours bar (used this period vs. budget), the reset period (monthly, weekly, or every N hours) and the next reset (UTC+8). When the budget runs out you can't start new GPU jobs or workspaces until the reset; running jobs continue.

    Which images a project can run¶

    Images you build are private to the project. A project can run:

    • images it built itself;
    • images of the platform, such as the ready-made IDE and desktop images;
    • public images from Docker Hub, GHCR and NVIDIA NGC, through the platform mirrors;
    • older images built before builds became private to each project: an image you built yourself works only in your personal project, and an image a group built works only in projects that group owns.

    An image another project built gives an Error row in Image security checks with Image security check refused: <ref>: built by another project; use this project's images, platform images or public mirrors. Rebuild it in your project, or ask its owner for the Dockerfile. A build whose FROM image belongs to another project is rejected the same way.

    Use private Docker Hub images¶

    A Project Manager connects a Docker Hub account once for the whole project:

    1. On Docker Hub, go to Account settings → Personal access tokens and create a token with Read-only access.
    2. In the project, open Settings → Docker Hub account, enter the Username and Access token, and click Save. The platform checks them with Docker Hub first and rejects a wrong pair with Docker Hub could not be reached with this username and token.
    3. Use the image as usual: image: <user>/<repo>:<tag> in a job, deployment or workspace, or docker run in the project's IDE.

    The section then reads Connected as <username>, updated <time>. The token is never shown again; to change it, save a new one. Remove asks for confirmation, disconnects the account and deletes the project's cached private images. Public Docker Hub images keep working either way. A Dockerfile FROM line can't use a private Docker Hub image; build from a public or platform base instead.

    Private images get the same security check, and only this project can use them. Every member's workloads can pull any private image of that account, so connect an account and token meant for the project.

    Image security checks¶

    The Overview tab has an Image security checks card listing the last 10 images your project's jobs and workspaces started, with a status for each:

    Status Meaning
    Checking The platform is still checking the image. The card refreshes by itself.
    Passed The image can run.
    Failed The platform blocked the image because a package in it is unsafe to run here.
    Error The check could not finish, for example the image or tag does not exist, or the check timed out.
    Unsupported The image comes from a registry the platform cannot check.

    The platform blocks an image only when it holds a package that endangers the platform. Known vulnerabilities in your own container do not block it. Each row also shows a one-line reason and when the image was last used. A Passed row says how many findings affect only your container and how many to upgrade first, for example 3 findings affect only this container (1 to upgrade first). When the platform has image checks turned off, the card says Image security checks are turned off.

    Click a row to see the upgrade list: each package, your installed version and the version to upgrade to, with the packages to upgrade first on top. A Failed row shows How to unblock with the packages that cause the block. Vulnerability IDs are not shown; only administrators see them. The other statuses have no details to open.

    A Failed row reads: <image>: blocked by the platform because <package> <version> is unsafe to run here. Upgrade it to <fix version> or later (rebuild on a newer base, or pick a newer tag). An Error row can also say the image was not found on Docker Hub, or that its registry is not supported; use Docker Hub, GHCR, NGC or this project's images.

    To fix a failure, rebuild on a newer base image tag, or upgrade the listed packages in the Dockerfile (apt, apk, dnf, pip) to at least the fixed version, then run the job again. For a public image, pick a newer tag. For a platform image, choose another version or contact the administrators.

    The card shows the latest result per image, and drops the oldest row when an 11th image is used.

    Config file versioning¶

    Every save creates a new version; old versions are kept. You can view or deploy any of them.

    Working with config files¶

    1. Go to Projects → [your project] → Config tab.
    2. Click New File, then upload a YAML file or paste content in the editor.
    3. Click the History icon next to a config to view all versions.
    4. To deploy a specific version, click Deploy on the version row.
    5. In the deploy dialog, pick the scheduling queue, and a reserved GPU claim for each claim slot in the YAML. The choice applies to this deploy only.

    Running instances show in the project's Resources tab, described below.

    A finished Pod is removed at most three days after it ends, with its entry and logs in Resources; the logs can vanish sooner (for example when a node restarts). A Job keeps its finished pods until you delete the Job. Save results to a mounted storage volume while the run is going.

    Containers you can shell into¶

    A Terminal needs a container that keeps running. A bare shell such as command: ["/bin/sh"] exits at once and restarts in a loop, so every terminal attempt fails.

    Give the container real work:

    command: ["sleep", "infinity"]

    or turn on stdin and tty under Interactive shell in the Resource Wizard (stdin: true and tty: true in raw YAML); the wizard warns about a bare shell.

    Then open the Resources tab, stay on Pods, and click Terminal on the row. Deployments and Jobs have no button; their running instance is under Pods.

    Deploy rules¶

    Quota counts everything you already have going, including workloads still waiting to start. Config files can deploy Pod, Deployment and Job; other kinds are rejected.

    Every container must set a memory request and limit of at least 128Mi, or deploy and dry-run validation rejects it. Write the unit: a bare memory: "1" means one byte.

    Asking for a GPU¶

    Two ways to ask for a GPU:

    • Inline GPU request. In the Resource Wizard, pick a GPU model in the container's resource settings. It counts toward your quota and must be a model your plan allows.
    • Reusable GPU claim. In the Resource Wizard, choose Pick at deploy and name the slot, for example train-a. In the deploy dialog, pick one of your GPU Claims for it.

    To give a claim to only some replicas, split them into separate Deployments. A config that asks for no GPU needs no allowed-model list and never gets a GPU claim.

    Advanced: writing the YAML yourself

    Leave the fields the platform manages out of your YAML: don't set metadata.namespace, metadata.generateName, metadata.ownerReferences or metadata.finalizers. For storage, use {{userVolume}} to mount your personal volume. Naming a volume directly works only in a group's project, and only for volumes that group already has.

    • Each pod gets one memory-backed /dev/shm, shared by its regular containers (not init containers), of up to 8 GiB or the pod's memory limit if that is smaller. It is skipped when any container in the pod already mounts something under /dev/shm.
    • An inline GPU request goes straight into the container's resource requests, for example nvidia.com/rtx6000: "1".
    • A GPU claim slot is an annotation on the Pod, or on the Deployment's template: platform-go/dra-claim-name: '{{ gpuClaimName "train-a" }}'. {{gpuClaimName}} with no name still works as the default slot. Two workloads can share a slot deliberately, or use different slots to get different claims.

    Config files and deployments require Project Manager role

    Only the Manager role or higher can create, edit, deploy, validate, inspect or delete config-file instances.

    Managing members¶

    1. Open the project and go to the Members tab.
    2. Click + Add Members (you need the Project Admin role).
    3. Search by username or email.
    4. Pick a role for each user:
    Role What they can do
    User Launch workspaces, view configs
    Manager Edit configs, manage deployments
    Admin Add/remove members, set member quotas
    1. Click Confirm to save.

    Project Admins can tick several rows to remove members, change roles or set per-user quotas in bulk. Managers and Admins see everyone's quota; a Project User sees only their own. A quota of 0 means no per-member limit; the project plan's cap still applies.

    Group-inherited members can be part of a bulk quota change, but not a bulk remove or role change; do those in the group.

    Removing a direct member also removes their workspace area in the project, storage permission overrides and per-user quota. To remove a group-inherited member, remove them from the group.

    Group inheritance and effective project role¶

    Your project role in a group-owned project:

    1. If you were added to the project directly, that role wins (admin / manager / user).
    2. Otherwise, on a personal project, the owner counts as admin.
    3. Otherwise, your group role in the owning group. A Group Admin is therefore a Project Admin on every project the group owns, without being added, and can set per-user quotas on the group's projects.

    When someone leaves the lab: ask an admin to remove them from the group. They lose every project they joined through it.

    Deleting a project¶

    Only a platform admin can delete a project, from Admin → Projects. Ask an admin or send a Request, and delete the project's workspaces first. Then:

    • The config version history and deployment records are gone for good.
    • Storage volumes are not deleted. They stay on the Storage page.

    Resources tab¶

    Your own resources. Cards at the top show your GPU, CPU and memory use. Below them is one tab per kind, each with a count: Pods (opens first), Services, Deployments, StatefulSets, Jobs, ConfigMaps, Secrets, Ingresses, ResourceClaims and RemoteDesktopSessions. Paused jobs sit at the top of Pods, since their Pod is gone until they resume. Delete all removes everything you have in the project and frees its quota.

    Everyone's resources. Project Admins, Project Managers and platform Admin/Manager roles get Personal and Members at the top of the tab. Members lists every other member:

    Column Meaning
    User Project member
    GPU Effective GPU units currently used
    CPU Requested or observed CPU cores
    Memory Memory in MiB
    Pod (the running instance) How many that member has running now

    Search by name, or expand a member to see what they run in the same kind tabs. Delete on a member's row removes all their resources and frees their quota. Project Users see only their own resources.

    On Pod rows, hover, focus, or tap the status badge for recent events, such as an image pull failure.

    GPU quota overview¶

    The Overview tab shows a quota bar per resource:

    Resource What It Tracks
    GPU Effective GPU units consumed vs. plan limit
    CPU CPU cores consumed by running workspaces
    Memory RAM consumed by running workspaces

    At 100% GPU, a new workspace waits in the queue until resources free up.

    Common questions¶

    I don't see a New Project button.

    Only users with the manage-projects permission see it. Ask an admin to create one.

    How do I view old config file versions?

    On the Config tab, click the clock icon (History) next to a config file. You see every past version with its time.

    My project quota is 0 GPUs. How do I get more?

    Send a Resource Request through Requests. An admin reviews it and attaches a Resource Plan to your project.

    What's the difference between a workspace's GPU and a GPU Claim?

    A workspace holds its GPU only while it exists. A GPU Claim is a separate reservation that persists across deployments; use one when several jobs need the same fractional GPU.

    Why is the Deploy button disabled?

    The project has no active plan, or its schedule window is closed (the default queue doesn't bypass it). The Plan tab shows the next opening.
