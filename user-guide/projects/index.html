    Projects¶

    Projects are the primary unit of resource allocation on the platform. Every workspace you launch consumes quota from a project, and every config file or deployment belongs to a project.

    Access: All authenticated users. A personal project is automatically created for you when you register.

    Project page layout¶

    Figure 1: Projects list in list view, the default.

    The Projects page supports two view modes:

    • List view (default) — compact table with sortable columns
    • Grid view — cards with project name, description, member count, GPU usage bar

    Toggle between views using the icons in the top-right of the toolbar.

    Create a project¶

    Creating a project requires the manage-projects permission. If you don't have it, the New Project button is hidden and the create page redirects back to your project list. Ask an admin to create a project for you instead. A personal project is created for you automatically when you register.

    1. Click Projects in the left sidebar.
    2. Click New Project (top-right button; shown only with the manage-projects permission).
    3. Fill in the project form:
    Field Description
    Name Short identifier (alphanumeric, hyphens allowed)
    Group Owning group (required)
    Description Optional — what this project is for
    1. Click Create. The project appears in your list immediately.

    Quota is assigned by an admin

    A new project starts with zero GPU quota. Contact your admin or submit a Request to have a Resource Plan bound to your project.

    Project detail tabs¶

    Click a project to open its detail page. The detail page includes core tabs for Overview, Config, Plan, Builds, GPU Claims, and Resources, plus role-dependent tabs such as Images, Members, Storage, and Settings.

    Figure 2: Project detail page with Overview, Config, Plan, Builds, GPU Claims, Resources, and role-dependent tabs.

    Tab Contents
    Overview Description, quota usage chart, monthly GPU-hour budget, current plan, member list summary
    Config Versioned config files describing what you want to run
    Plan Bound resource plan, schedule window, allowed GPU models, and quota envelope
    Builds Project-scoped image builds, archive or Dockerfile source selection, shared queue status, and live build logs
    GPU Claims Reusable GPU reservations you can prepare in advance and attach to a deployment later
    Resources Live per-member GPU/CPU/memory usage, expandable to what each member is running
    Images / Members / Storage Additional tabs shown when your role allows image management, membership management, quota controls, or storage access
    Settings Project-wide workspace controls; see Project settings below

    Role thresholds: the Storage, Images, and Settings tabs require Project Manager or above; the Members tab is visible to Project Admins only (platform admins must switch to Admin View via the avatar menu to be treated as an effective Project Admin). The platform prevents an Admin from demoting themselves, so a project can never lose its last Admin.

    Project settings¶

    The Settings tab (Project Manager or above) holds controls that apply to every workspace in the project:

    Field What it does
    Max workspace continuous runtime In seconds. A workspace that has run longer than this is stopped automatically. 0 means unlimited (the default).

    Click Save Changes to apply. The limit also caps the lifetime of GPU desktops started from this project.

    Build project images¶

    Use the Builds tab when a project needs a container image that is not already in the allowed image list. Project Managers and Project Admins can start builds when image builds are enabled for the project. Project Members can view build status and logs, but cannot start or delete builds.

    Source options¶

    Source When to Use It
    Upload archive Upload a .tar.gz or .zip build context. Put the Dockerfile at the archive root.
    Dockerfile only Paste a Dockerfile directly. The platform creates a minimal build context.

    Build settings¶

    Field Notes
    Image Name Short repository name, for example trainer-api. The final registry path is generated by the platform.
    Tag Optional. Leave empty for the platform default, or set a release tag such as v1.0.1.
    Build source Upload archive or pasted Dockerfile.

    Builds are submitted to a shared queue and run one at a time. Each build gets a fixed amount of CPU, memory, and scratch space that you cannot change from the form, and that capacity does not consume your project or personal quota.

    Uploaded archives are checked for unsafe paths and size limits before the build starts.

    The build history shows status, source type, destination image, and live logs. Failed builds show a short summary in the table. Use the log button for the full output. If a build is retried, the log view keeps the previous attempt's failure reason before streaming the current one.

    Each build row has icon actions: Cancel build while it is running (or Delete image artifact once it has produced an image), Clear saved logs, and Delete history record. Builders and project managers can clear saved logs for completed or failed builds; build history and images are left untouched. The member who started a completed build, or a project manager, can also delete its history record once nothing else references it.

    Project Managers can submit project image allowlist requests and remove project image allowlist entries only for projects they currently manage. Project Members can view the project's image request history, but global catalog publications and other projects' image rules remain admin-controlled.

    The Images tab splits into Available and Requests. Available lists the images this project may already pull. Requests lists every image request raised for the project, pending ones first, with its status, submission time and reviewer note; the tab label carries a badge with the pending count. Submitting a request through Add switches you to that tab so the new request is visible immediately.

    A request you filed yourself can be taken back with Withdraw while it is still pending; you can submit it again afterwards. Requests filed by someone else, or already approved or rejected, offer no withdraw action.

    Approved-as-global requests leave the project list

    When an admin approves a request and ticks Make global, the request stops being project-scoped and disappears from this tab. The image itself then appears under Available.

    Build access is project-governed

    If the start form is hidden, the project either does not have Image Build Permission enabled or your project role cannot start builds. Build history and logs remain visible so you can still inspect previous jobs. Ask a project manager or platform admin to adjust the project setting or your role.

    GPU Claims¶

    The GPU Claims tab lists GPU reservations you can prepare for a project before deploying anything. A claim reserves GPU quota the moment you create it, but only starts counting GPU-hours once it is attached to a running workload. You can pick a claim in the deploy dialog whenever a config file declares a GPU claim slot.

    Create a claim¶

    Fill in the Create GPU ResourceClaim form and click Create:

    Field Notes
    Claim name Name used when you attach this claim to a deployment. Letters, digits, and hyphens only.
    GPU device class The GPU model to reserve. The form defaults to a specific model; pick Any only when the model does not matter.
    GPU count How many physical cards this claim reserves. A multi-GPU claim stays a single reservation.
    SM share Compute slice from 1% to 100%. The resulting effective GPU count is shown beside the form.
    VRAM mode Elastic shares GPU memory with other workloads; Hard cap enforces the percentage you pick.
    VRAM share Used only with Hard cap. The reserved memory is derived from the smallest card of the selected model.

    Every replica of a Deployment shares the same claim. A 2-GPU claim stays one 2-GPU reservation no matter how many replicas run, and quota and GPU-hours are counted once per claim rather than once per replica.

    A claim that is not attached to anything uses 0 GPU-hours but still counts against project and per-user GPU quota. The table columns are Name, Owner, GPU, SM, VRAM, Status, and Allocation, plus a delete icon. Status is Reserved (created, nothing attached), Allocated (a GPU is assigned), or In use by . Unused claims can be deleted; a claim in use by a running workload cannot.

    Claim ownership

    Project Members can create their own claims. Project Managers can also see and delete claims belonging to other members of the project.

    Plan window countdown¶

    When a project's resource plan defines a schedule window, the Plan tab shows a live countdown to the next boundary:

    • Window closes in HH:MM:SS while the window is open.
    • Window opens in HH:MM:SS when the next window is upcoming.
    • Always active if no schedule restriction is defined.

    The deploy dialog shows the same countdown (Plan window closes in HH:MM:SS) with a warning that the workload may be evicted when the window closes. Once it has closed, the dialog shows Plan window has expired with a Switch to Default Queue link that moves the deploy to the default queue; this banner is for deployments only, workspaces cannot switch queue. When the window closes, workloads in plan-bound queues are stopped; if the plan is removed or stops allowing your queue, anything still waiting to start is dropped too. A project with no active plan cannot start workloads at all.

    Queues may also carry a runtime limit. When the queue you selected has one, your workload is stopped automatically after that many seconds. The limit is set by an admin and cannot be raised or disabled from your config file.

    The Overview tab also shows the plan's GPU-hours / month bar when the plan has a monthly GPU-hour budget: allocated GPU-hours this month against the budget, and when it resets (the 1st of each month, UTC+8). Once the budget is used up, new GPU jobs and workspaces are blocked until the reset; running jobs are unaffected.

    Config file versioning¶

    Every save creates a new, immutable version. Old versions are never overwritten, so you can always look back at an earlier one, or redeploy it. Edit or upload a config file, save it, and a new version appears; you can deploy any version.

    Working with config files¶

    1. Go to Projects → [your project] → Config tab.
    2. Click New File to upload a YAML file or paste content in the editor.
    3. Each save creates a new version.
    4. Click the History icon next to a config to view all versions.
    5. To deploy a specific version, click Deploy on the version row.
    6. In the deploy dialog, pick the scheduling queue. If the YAML contains GPU claim slots, choose one of your reserved GPU claims for each slot for this deploy only.

    Running instances appear in the project's Resources tab. A separate Deployments page at /projects/<project id>/deployments lists deployments with Personal and Members tabs; it has no sidebar link, so open it by URL.

    Containers you can shell into¶

    To open a Terminal into a container, it has to stay running. A shell with no arguments, such as command: ["/bin/sh"], exits immediately, so the container restarts over and over and every terminal attempt fails.

    Either give the container real work:

    command: ["sleep", "infinity"]

    or keep the shell alive by enabling stdin and tty under Interactive shell in the Resource Wizard (stdin: true and tty: true in raw YAML). The wizard warns you when a bare shell would exit immediately.

    Once the container is running, open the project Resources tab and click Terminal on the Pod row. Deployment and Job rows have no terminal button. Expand them to reach the running instance they created.

    Deploy rules¶

    Deploying, validating, inspecting, and deleting config-file instances needs the Project Manager role or higher. Quota is checked against everything you already have in flight, so a workload still waiting to start keeps holding its share until it finishes or is removed. Config files can deploy Pod, Deployment, and Job workloads; other kinds are not accepted.

    Every container must set both a memory request and a memory limit of at least 128Mi; missing values are rejected during deploy and dry-run validation. Always include the unit: a bare memory: "1" means one byte and is rejected.

    Asking for a GPU¶

    There are two ways a config file can ask for a GPU.

    • Inline GPU request. In the Resource Wizard, pick a GPU model in the container's resource settings. The platform counts it toward quota, checks the model against your plan's allowed models, and sets up the GPU when you deploy.
    • Reusable GPU claim. In the Resource Wizard, choose Pick at deploy and give the slot a name such as train-a. The slot name is only a label; you map it to one of your own claims from the GPU Claims tab in the deploy dialog.

    Every replica of a Deployment shares one claim. If only some replicas should use a claim, split them into separate Deployments. Configs that request no GPU need no allowed-model list, and never receive a GPU claim.

    Advanced: writing the YAML yourself

    Leave platform-owned fields out of your YAML: do not set metadata.namespace, metadata.generateName, metadata.ownerReferences, or metadata.finalizers. For storage, use {{userVolume}} to mount your personal volume; naming a volume directly works only in group-owned projects, and only for volumes the owning group already has.

    • An inline GPU request goes straight into the container's resource requests, for example nvidia.com/rtx6000: "1".
    • A GPU claim slot is an annotation on the Pod, or on the Deployment's template: platform-go/dra-claim-name: '{{ gpuClaimName "train-a" }}'. {{gpuClaimName}} with no name still works as the default slot. Two workloads can share a slot deliberately, or use different slots to get different claims.

    Config files and deployments require Project Manager role

    Only project members with Manager or higher role can create, edit, deploy, validate, inspect, or delete config-file instances.

    Managing members¶

    1. Open the project and go to the Members tab.
    2. Click + Add Members (requires Project Admin role).
    3. Search for users by username or email.
    4. Select a role for each user:
    Role What they can do
    User Launch workspaces, view configs
    Manager Edit configs, manage deployments
    Admin Add/remove members, set member quotas
    1. Click Confirm to save.

    Project Admins can select several rows at once to remove members, change roles, or set per-user quotas in bulk. Managers and Admins can see everyone's quota; a Project User sees only their own. A quota of 0 means that resource is unlimited for that member, still capped by the project plan.

    Group-inherited members. Members who joined through the owning group can be included in a bulk quota change, but not in bulk remove or role changes; their membership and role are managed in the group instead.

    Removing a direct member also removes their workspace area in the project, any project storage permission overrides, and their per-user quota. Group-inherited members must be removed from the owning group instead.

    Group inheritance and effective project role¶

    When a project is owned by a group, the platform resolves each caller's effective project role as follows:

    1. If the user has an explicit project member record, that role wins (admin / manager / user).
    2. Otherwise, for personal projects, the personal owner is treated as admin.
    3. Otherwise, the user's group role in the owning group is used as the effective project role. A Group Admin therefore acts as a Project Admin on every project owned by that group, even without being added to the project directly.

    This is why a Group Admin can set per-user quotas on a project owned by their group, and see the batch selection controls in the Members tab, without being added as a direct member.

    Offboarding tip: when someone leaves the lab, ask an admin to remove them from the owning group. Access to every project joined through that group disappears automatically, with no per-project cleanup.

    Deleting a project¶

    Only a platform admin can delete a project, from Admin → Projects. There is no delete action on the project page. Ask an admin, or submit a Request; delete the project's workspaces first. Effects:

    • Config version history and deployment records are permanently removed.
    • Storage volumes are not deleted (they remain on the Storage page).

    Resources tab¶

    The Resources tab summarizes live usage by project member:

    Column Meaning
    User Project member
    GPU Effective GPU units currently used
    CPU Requested or observed CPU cores
    Memory Memory in MiB
    Pod (the running instance) How many that member currently has running

    Project Admins, Project Managers, and platform Admin/Manager roles see every project member; regular Project Users see only their own row. Expand a row to inspect what is running, or terminate the resources you are allowed to manage. Terminating a workload here releases the quota it was holding.

    For Pod rows, hover, focus, or tap the status badge to see recent events. This helps when a workload looks like it is still starting but is really failing to pull its image.

    GPU quota overview¶

    The Overview tab shows a quota bar for each resource type:

    Resource What It Tracks
    GPU Effective GPU units consumed vs. plan limit
    CPU CPU cores consumed by running workspaces
    Memory RAM consumed by running workspaces

    If the GPU bar is full (100%), new workspace launches will queue and wait for resources to free up.

    Common questions¶

    I don't see a New Project button.

    The button is shown only to users with the manage-projects permission. If you don't have it, ask an admin to create a project for you. Your personal project is created automatically when you register.

    How do I view old config file versions?

    On the Config tab, click the clock icon (History) next to any config file to see all past versions with their timestamps.

    My project quota is 0 GPUs. How do I get more?

    Submit a Resource Request via Requests. An admin will review and bind a Resource Plan to your project.

    What's the difference between a workspace's GPU and a GPU Claim?

    A workspace reserves its GPU only for as long as the workspace exists. A GPU Claim is a standalone reservation that survives across deployments. Use one when several jobs need the same fractional GPU and you want to avoid rescheduling churn.

    Why is the Deploy button disabled?

    Either the project has no active plan bound, or the plan window is currently closed and only the default queue is selectable. Check the Plan tab for the next opening time.
